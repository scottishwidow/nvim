# Feature Specification: Basic Pre-Commit Hooks

**Feature Branch**: `worktree-002-pre-commit-hooks`

**Created**: 2026-11-10

**Status**: Draft

**Input**: User description: "I want to add basic pre-commit hooks for this project using pre-commit framework."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Block common file hygiene problems at commit time (Priority: P1)

A contributor commits changes to the configuration. Before the commit is recorded, automatic checks find common problems in the staged files: trailing whitespace, a missing final newline, unresolved merge conflict markers, unintentionally large files, and malformed structured data files (JSON, YAML, TOML). Where a fix is safe and mechanical, the check fixes the file. The contributor reviews the fix, stages it, and commits again.

**Why this priority**: These problems are the most frequent cause of noisy diffs and broken configuration loads. Catching them before the commit gives the most value for the least effort.

**Independent Test**: Stage a file with trailing whitespace and a JSON file with a syntax error, then try to commit. The commit is blocked, the whitespace is removed, and the JSON error is reported with the file name.

**Acceptance Scenarios**:

1. **Given** a staged file with trailing whitespace, **When** the contributor commits, **Then** the commit is blocked, the whitespace is removed from the file, and the contributor is told which file changed.
2. **Given** a staged JSON, YAML, or TOML file with invalid syntax, **When** the contributor commits, **Then** the commit is blocked and the message names the file.
3. **Given** a staged file that contains merge conflict markers, **When** the contributor commits, **Then** the commit is blocked.
4. **Given** staged files with no problems, **When** the contributor commits, **Then** the commit succeeds with no changes to the files.

---

### User Story 2 - Enforce consistent Lua formatting (Priority: P2)

A contributor edits a Lua file of the configuration. At commit time, the staged Lua files are checked against the formatting rules that the project already defines. Files that do not match are formatted automatically and the commit is blocked so that the contributor can review and stage the result.

**Why this priority**: Lua is the main code in the project, and the project already has a formatting rule file. Enforcing it keeps diffs small, but the configuration still works without it, so it ranks below basic hygiene.

**Independent Test**: Stage a Lua file with wrong indentation, then try to commit. The commit is blocked and the file is reformatted to match the project rules.

**Acceptance Scenarios**:

1. **Given** a staged Lua file that does not match the project formatting rules, **When** the contributor commits, **Then** the commit is blocked and the file is reformatted.
2. **Given** a staged Lua file that matches the project formatting rules, **When** the contributor commits, **Then** the Lua check passes.

---

### User Story 3 - Run all checks on demand (Priority: P3)

A contributor wants to check the whole repository, not only staged files, for example after the hooks are first added or before opening a pull request. The contributor runs one command and gets the result of all checks for all tracked files.

**Why this priority**: Useful for the first cleanup and for occasional audits, but daily work depends on the commit-time checks.

**Independent Test**: Run the on-demand command on a clean checkout. All checks run against all tracked files and report pass or fail for each check.

**Acceptance Scenarios**:

1. **Given** a checkout with the hooks installed, **When** the contributor runs the on-demand command, **Then** every check runs against all tracked files and reports a result.

---

### Edge Cases

- A contributor has not installed the hooks locally: commits are not checked. Setup steps must be short and clear so that this case is rare.
- A file is generated by a tool and must keep its exact content (for example the plugin lock file): checks must not rewrite it in a way that the generating tool later reverts.
- Vendored or tool-managed directories (for example spec tooling files under `.specify/` and agent skill files): checks that would change these files must exclude them, or the first full run must fix them in one separate commit.
- The Lua formatting tool is not available on the contributor's machine: the check must get the tool automatically or fail with a clear message, not pass silently.
- A contributor must commit urgently while a check fails: the standard skip mechanism of git remains available, but project rules forbid its routine use.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The project MUST use the pre-commit framework to define and run commit-time checks, with one configuration file at the repository root.
- **FR-002**: The checks MUST remove trailing whitespace and add a missing final newline in text files.
- **FR-003**: The checks MUST reject unresolved merge conflict markers.
- **FR-004**: The checks MUST validate the syntax of JSON, YAML, and TOML files.
- **FR-005**: The checks MUST reject files larger than a set size limit (default: 500 KB).
- **FR-006**: The checks MUST verify that staged Lua files match the formatting rules in the existing project formatting file, and reformat files that do not match.
- **FR-007**: Each external hook source MUST be pinned to an exact released version or full commit identifier, in line with the project supply-chain rules in `SECURITY.md`.
- **FR-008**: The checks MUST run only on staged files during a commit, and on all tracked files when run on demand.
- **FR-009**: When a check fails, the output MUST name the check and the affected files.
- **FR-010**: The repository MUST pass all checks on all tracked files after the feature is complete.

### Key Entities

- **Hook configuration**: The single file that lists each check, its source, its pinned version, and any file exclusions.
- **Check**: One automatic rule that inspects staged files and passes, fails, or fixes them.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A new contributor can enable the checks in under 2 minutes with at most 2 commands.
- **SC-002**: 100% of the failure types in the acceptance scenarios block the commit.
- **SC-003**: The checks finish in under 10 seconds for a typical commit of up to 10 files, after the first run.
- **SC-004**: A full on-demand run on the current repository reports zero failures after the feature is complete.
- **SC-005**: Every external hook source has an exact version pin (0 floating references).

## Assumptions

- Scope is local commit-time checks only. Running the checks in continuous integration is out of scope for this feature.
- "Basic" means file hygiene, structured-data syntax, and Lua formatting. Lua static analysis (linting), spell checking, and Markdown linting are out of scope.
- Lua formatting uses the rules in the existing `stylua.toml` file. No change to those rules is part of this feature.
- Contributors have Python available, which the pre-commit framework requires.
- The first full run can change existing files (whitespace, final newlines, Lua formatting). These changes go in a separate commit from the hook configuration.
- Documentation of the setup steps is limited to what the user asks for; no new documentation file is part of this feature unless requested.
